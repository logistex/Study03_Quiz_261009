# 점검 장치 guard

guard는 클로드가 되풀이하는 실수를 그 자리에서 멈춰 세우려고 필자가 실습한 컴퓨터의 클로드 코드에 설치한 확장 프로그램임. 학생 환경에는 없으므로 설치할 필요가 없음. 보고서에서 「guard가 막았음」, 「[guard] 답을 고치는 중임.」 같은 장면을 읽을 때 이 문서를 참고하면 됨.

- 이 문서는 이 폴더의 코드(`hooks/` 아래 4개 파일, 2026-10-07 판)를 읽고 썼음
- 표의 「번호」(G1, G3 등)는 guard 안에서 점검마다 붙인 번호이며, 코드의 주석에 같은 번호가 있음

## guard가 하는 일

guard는 클로드 코드가 일하는 도중의 4개 시점에 점검을 걸어 두고, 조건에 걸리면 클로드에게 고칠 점을 알림.

| 시점 | guard가 하는 일 | 보고서에 나온 곳 |
|---|---|---|
| 사용자가 메시지를 보낼 때 | 메시지에 질문이 있으면 「도구를 부르기 전에 질문에 먼저 답할 것」이라는 메모를 클로드의 입력에 덧붙임 | 없음 |
| 클로드가 도구를 부르기 전 | 아래 「도구를 부르기 전에 막는 일」의 조건에 걸리면 그 호출을 막고 이유를 클로드에게 돌려줌 | 보고서 3.2절, 4.2절(푸시가 막힘) |
| 클로드가 스킬을 부를 때 | 구현을 실행하는 스킬의 결과 뒤에 「계획과 다르게 정할 일이 생기면 멈추고 여쭐 것」 등의 문장을 덧붙임 | 보고서 3.1절, 3.2절 |
| 클로드가 답을 끝내려 할 때 | 답 글을 화면에 내보내기 전에 검사하고, 걸리면 답을 한 줄로 바꾼 뒤 클로드에게 다시 쓰게 함 | 보고서 1.3절, 7.3절 |

- 같은 점검은 한 차례(사용자의 메시지 1개부터 클로드의 답이 끝날 때까지)에 한 번만 막음. 막힌 뒤 클로드가 고쳐서 다시 시도하면 통과함
- 그러므로 guard는 일을 끝까지 못 하게 막는 장치가 아니라, 한 번 멈춰 세워 고칠 기회를 주는 장치임

## 도구를 부르기 전에 막는 일

| 번호 | 막는 일 | 조건 | 막는 이유 |
|---|---|---|---|
| G1 | 질문에 답하지 않고 작업을 시작함 | 사용자의 메시지에 질문이 있는데, 클로드가 답 글을 쓰지 않고 도구부터 부름 | 질문에 답하지 않고 작업으로 넘어가는 일이 되풀이됨 |
| G7 | 할 일의 순서를 밝히지 않음 | 메시지에 할 일이 2개 이상인데, 답 글에 순서를 밝히는 말(먼저, 그다음 등)이 없음 | 물어본 것부터 답하고 오래 걸리는 일을 나중에 하게 함 |
| G3 | 승인 없이 밖으로 내보냄 | 푸시(`git push`), 저장소나 PR 만들기, 노션 편집, DB 변경을 하려는데, 그 차례의 메시지에 승인 표현이 없음 | 되돌리기 어려운 일은 사람이 직접 승인한 뒤에 하게 함 |
| G12 | 어림한 시각을 씀 | 파일에 `11:4x`처럼 분 자리를 x로 쓴 시각을 쓰려 함 | 확인하지 않은 시각이 기록에 남는 일이 되풀이됨 |
| G9 | 계획과 다른 결정을 기록만 하고 넘어감 | 작업 기록 파일에 `Ruling:` 줄(계획과 다르게 정한 결정)을 쓰려 함 | 계획을 바꾸기 전에 사람에게 묻게 함 |
| G5 | 노션을 편집 도구로 직접 고침 | 노션 페이지 편집 도구를 부름 | 그 도구로 보내면 한글이 깨진 사례가 되풀이됨 |

- G3의 승인 표현은 「올려」, 「푸시해」, 「진행해」, 「그대로」와 그 이음꼴(올리고, 진행하자 등)임
  - 같은 문장에 부정하는 말(말고, 하지, 않 등)이 있으면 승인으로 보지 않음
  - 붙여 넣은 글과 코드 블록 안의 승인 표현은 세지 않음. 보고서 4.2절에서 푸시가 한 번 더 막힌 이유임
  - 「진행」처럼 목록에 없는 말은 승인으로 보지 않음. 보고서 3.2절에서 푸시가 막힌 이유임
- 그 밖에 필자의 다른 작업(guard 자신을 고치는 저장소)에만 해당하는 점검 2개(G13, G14)가 있으나, 이번 실습에는 해당하지 않음

## 스킬에 덧붙이는 문장

- 클로드가 구현 계획을 실행하는 스킬(`executing-plans`, `subagent-driven-development`)을 부르면, guard가 스킬의 결과 뒤에 다음 내용을 덧붙임(번호 G15)
  - 계획과 다르게 정할 일이 생기면 혼자 정해 기록만 남기지 말고, 멈추고 사람에게 여쭐 것
  - 태스크 하나를 끝내면 그 차례를 끝내고 답을 기다릴 것
  - 태스크마다 바뀐 것, 시험 결과, 남은 일을 보고할 것
- 이 스킬은 원래 태스크 사이에 멈추지 말고, 계획과 다른 결정은 기록만 남기고 진행하라고 지시함. guard는 그 지시를 따르지 않게 하려고 이 문장을 넣음
- 보고서 3.1절은 1단계 구현 세션의 클로드가 구현 전에 브랜치를 물은 일이 이 문장에서 비롯되었을 가능성을 다룸
- 보고서 3.2절은 이 문장이 있었는데도 클로드가 묻지 않고 병합한 일을 다룸. 일반적인 문장만으로는 구체적인 행동을 막지 못한 사례임

## 답을 내보내기 전에 하는 검사

- 클로드가 도구를 부르지 않고 답을 끝내려 하면, guard는 답 글을 화면에 내보내기 전에 다음을 검사함

| 번호 | 검사 | 판정 방법 |
|---|---|---|
| G2 | 설명 없이 쓴 이름(커밋 해시, 문서 이름 없는 절 번호, 작업 중에 붙인 이름), 뜻이 안 읽히는 문장, 근거 없이 두 일을 잇는 말 | 정해진 꼴을 찾는 검색과, 300자 이상인 답이면 작은 모델(Haiku)의 판정 |
| G4 | 화면을 보지 않고 쓴 화면 조작 절차(무엇을 누르라는 안내) | 그 차례에 화면을 찍거나 그림을 본 적이 있는지 |
| G6 | 고쳤다고 했으나 고친 뒤 다시 읽지 않은 파일 | 답 글의 「고쳤」, 「반영했」 같은 말과, 그 차례의 파일 편집과 읽기 기록 |
| G12 | 어림한 시각 | `11:4x` 꼴을 찾는 검색 |

- 하나라도 걸리면 guard는 답 글 대신 「[guard] 답을 고치는 중임.」 한 줄만 화면에 내보내고, 고칠 점을 클로드에게 알려 답 전체를 다시 쓰게 함(번호 G16)
  - 보고서의 대화 기록에 이 한 줄이 남아 있는 곳은 guard가 원래 답을 막은 자리이며, 다시 쓴 답은 그 뒤에 나옴(보고서 1.3절)
  - 같은 답이 화면에 두 번 나오지 않게 하려고, 걸린 답을 지우지 않고 한 줄로 바꾸는 방식을 골랐음

## 알려진 문제

| 문제 | 내용 | 상태 |
|---|---|---|
| 다시 쓰라는 알림이 오지 않음 | 답을 한 줄로 바꾼 뒤 클로드에게 다시 쓰라는 알림이 가지 않아, 세션이 다음 메시지를 받을 때까지 멈춘 일이 있음. 11번 세션(명령어 세션)은 2시간 56분 멈췄음 | 원인을 찾지 못함(보고서 7.3절) |
| 헛경보 | 화면 조작 절차가 아닌 문장을 절차로 보거나, 이미 설명한 이름을 설명 없는 이름으로 보는 일이 있음 | 코드의 주석에 고친 사례가 날짜와 함께 적혀 있음 |

## 파일 구성

| 파일 | 내용 |
|---|---|
| `hooks/register.ts` | 4개 시점에 점검을 거는 코드. 어느 시점에 무엇을 막는지가 이 파일에 모여 있음 |
| `hooks/detect.ts` | 질문, 승인 표현, 푸시 명령, 어림한 시각 등을 찾는 판정 함수 |
| `hooks/state.ts` | 한 차례 동안 점검들이 함께 쓰는 값(질문, 승인 여부, 고친 파일 등) |
| `hooks/stop.ts` | 답을 끝내기 전에 하는 검사 |
| `hooks/hooks.json`, `.claude-plugin/plugin.json`, `tsconfig.json` | 설정 파일 |

- 시험 파일(`tests/`)은 지난 대화의 메시지를 담고 있어 올리지 않았음
- 이 코드는 실습한 컴퓨터의 확장 설치 방식에 맞춰 쓴 것이라, 이 폴더를 내려받아도 그대로 설치되지는 않음
